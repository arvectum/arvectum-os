## 2. Why UI4 uses a real preflight rather than a fabricated mutation

The selected runtime already retains one real UI1 governed `platform.document` with exact Subject/Version identity, External Reference authority, execution/Event provenance and checkpoint evidence. Its P7.03 minimized persistence deliberately does not contain every historical field needed to reconstruct an arbitrary full `CanonicalRecord` or a new action-specific `GovernedInteractionCase` without invention.

UI4 therefore does **not** guess missing governed fields and does **not** create a synthetic successful mutation merely to satisfy a UI proof. It implements the roadmap-permitted bounded **preflight** over the real retained state:

1. re-authorize exact UI1 read access and UI2/P7.04 human technical interaction access;
2. re-verify the immutable P7.03 manifest and minimized payload;
3. verify exact retained Subject/Version, authority, execution, Event, provenance and checkpoint continuity;
4. present the four action-decision categories as `Waiting` because UI4 supplies no action-specific Authorization, Organizational Authority, Data Governance or Consequential Approval;
5. accept only a bounded owner browser POST that re-runs this preflight and records minimized non-canonical evidence;
6. perform no canonical mutation or product/external effect.

This keeps technical access distinct from organizational authority and avoids inventing governance evidence.
