This review is a bounded remediation of the already-closed P7.06 owner-operated deployment path after new UI3 operational evidence exposed a recoverability gap. ## 1. Trigger evidence

The selected-Mac forensic run reported:

- forensic classification: `UPDATE_COMMAND_FAILED`;
- canonical `origin/main`: `ec649b8df8b90444162590dbaeed0b2b79aeaae6`;
- `current` before/after the forensic update command: `d5cb521bf2565c42ad8ccf47565dda18cf9106c6`;
- live P7.02 health release: `6d4d07aead603841ecce3c469dd46f5e0d58ccd5`;
- P7.02 health failure: release mismatch, exit code `7`;
- no new P7.06 rollback/recovery evidence during or after the failed command;
- P7.03 and P7.04 digests unchanged;
- live persistent runtime PID remained unchanged throughout the forensic observation.

These are bounded owner-operator task-material facts. They establish that the latest attempted `update` did not start a new P7.06 deployment transaction: canonical `update_runtime()` fails closed at the initial `P7.02 status` check when `current` and live health disagree.

## 2. Canonical implementation finding

Canonical P7.02 status derives the expected release from the `current` symlink and asks the exact current release health checker to verify that the live health telemetry reports the same release. A mismatch returns health exit code `7`.

Canonical P7.06 update runs that P7.02 status check before preparing a new target, acquiring the deployment lock, backing up P7.03 or mutating runtime lifecycle state. Therefore the forensic `UPDATE_COMMAND_FAILED` result is correctly fail-closed and does not itself represent an automatic rollback.

The existing `recover-interrupted-latest` command is not a suitable blind repair for this state. It selects the latest P7.06 work directory containing pre-runtime/pre-observer plists and restores its source release. The new evidence instead identifies a different and narrower recoverability need: reconcile `current` to a release already proven to be the live exact P7.02/P7.05 release, without guessing from work-directory recency.

## 3. Remediation boundary

`reference/python/p7_06_runtime_consistency_recovery.py` repairs only this bounded mismatch.

Before mutating `current`, it requires all of the following:

1. execution on macOS;
2. clean canonical `arvectum/arvectum-os` checkout on `main` with `HEAD == origin/main`;
3. exclusive acquisition of the existing `run/p7-06-deploy.lock` namespace;
4. owner-only exact runtime and observer LaunchAgent plists;
5. exact P7.02 launchd `--runtime-root` and `--release-sha` pin;
6. exact release Python/runtime source paths matching that release;
7. exact P7.05 observer Python/source/runtime-root pin matching the same release;
8. immutable installed release manifest identifying `arvectum/arvectum-os` and that exact release;
9. a live P7.02 launchd PID;
10. exact-release P7.02 health `PASS` for that release;
11. health PID exactly equal to the launchd PID;
12. `current` currently differs from this proven live release.

Only after those conditions pass does recovery atomically replace the `current` symlink so it points to the **already-running proven release**. It does not choose canonical main, a newer release, a work-directory source or an arbitrary operator-supplied release.

Post-mutation gates require:

- P7.02 status PASS;
- P7.05 observer status PASS;
- `current` remains the proven running release;
- P7.03 governed/checkpoint digest unchanged;
- P7.04 access/credential digest unchanged.

The tool emits owner-only non-canonical recovery evidence plus SHA-256 and records that it did not restart the runtime, reinstall the observer, invoke governed update/rollback, invoke UI3 lifecycle behavior, mutate canonical organizational state, create authority/approval, invoke product/external effects or replay historical effects.

## 4. Why this is not a deployment bypass

The remediation deliberately restores internal consistency **backward to the release already executing**, rather than activating a target release. It cannot advance the runtime to canonical `main`.

After recovery, normal `p7_06_macos_deploy.sh update <decision-ref>` remains the only path used to advance to canonical main. Therefore the remediation restores the precondition required by the existing governed deployment controller rather than replacing it.

## 5. Functional review/revise

### Iteration 1 — recovery target authority

Concern: a pointer-repair command could become an undeclared arbitrary release selector or bypass P7.06 governed update semantics.

Resolution:

- no target-release argument exists;
- target release is derived only from the exact P7.02 launchd plist;
- P7.05 observer pin must independently match it;
- live health release and PID must match launchd;
- installed release manifest must match canonical repository/release identity;
- the command fails when `current` is already consistent;
- canonical main activation remains outside this helper.

Result: `PASS`.

### Iteration 2 — state/evidence safety

Concern: recovery must not silently alter P7.03/P7.04 or become unobservable operational magic.

Resolution:

- P7.03 governed/checkpoint and P7.04 registry/secret digests are captured before and after;
- any mismatch fails recovery;
- recovery uses the existing P7.06 deployment lock namespace;
- owner-only evidence and SHA-256 are written under a dedicated recovery evidence directory;
- reusable secrets are never emitted.

Result: `PASS`.

### Iteration 3 — operational coexistence

Concern: observer state could remain pinned to another release even if P7.02 is healthy, producing a new mixed-release state after pointer repair.

Resolution:

- exact observer plist release pin is independently parsed and must equal the proven P7.02 release before any mutation;
- P7.05 observer status must pass after pointer reconciliation.

Result: `PASS`.

No material repository-scope objections remain after iteration 3. Selected-Mac recovery execution and subsequent ordinary P7.06 update are still required operational evidence.
