## Declared scope

`P7.06-UI3 — Persistent private operator access` establishes a bounded owner-operated persistent presentation process around the already accepted UI1/UI2 repository implementation. It does not create a public/stable interface, a real UI4 interaction provider, Organizational Authority, consequential approval, canonical mutation, Product Contract, or Platform Capability lifecycle transition.

## Review/revise loop

### Iteration 1 — listener/process attribution

Material objection: the first shell status check proved only that *some* listener existed on the configured loopback port. If the UI3 process failed to bind while another local process occupied that port, the check could falsely pass.

Revision: status now extracts the running PID from the exact launchd job, requires that PID to be alive, requires `lsof` to show the listener owned by that PID, requires the address to be exactly `127.0.0.1:<port>`, and rejects any second process/listener sharing the port. Regression coverage was added.

Result: objection resolved.

### Iteration 2 — exact-release update/rollback continuity

Material objection: a persistent UI3 process pinned to release A would become stale if the existing P7.06 governed deploy path advanced or rolled back `current` without coordinating the presentation process.

Revision: UI3 adds an outer owner-operated `governed-update` / `governed-rollback-last` lifecycle wrapper. It stops only the non-canonical UI3 presentation process, delegates the canonical deployment mutation unchanged to the existing exact-release `p7_06_macos_deploy.sh`, then reconciles UI3 against the resulting exact release. If the resulting release contains UI3, it installs/verifies the exact-release UI3 service; if rollback reaches a pre-UI3 release, UI3 private material/logs are removed and the service remains absent. Failed P7.06 update/rollback is followed by reconciliation against whichever release the governed deploy adapter leaves current.

The underlying P7.06 deployment transaction, backup/restore semantics, observer/runtime ordering and canonical mutation rules are not forked or reimplemented.

Result: objection resolved for the declared owner-operated UI3 path.

### Iteration 3 — authorization, authority and interaction boundary

Checks:

- install requires an already existing enabled **human** P7.04 credential with exact local UI1 `workspace.inspect` and UI2 `workspace.interact` grants;
- UI3 does not create grants or credentials and re-runs the UI1/UI2 authorization helpers before serving;
- technical access remains distinct from Organizational Authority and consequential approval;
- the UI3 ingress secret is separate from P7.04 credentials, owner-only, absent from config/launchd arguments/HTTP logs, and exchanged only for a random process-local browser session;
- protected requests remain behind loopback Host checks; unlock POST also requires same-origin plus CSRF; UI2 retains its own same-origin/CSRF and per-request governed preflight controls;
- restart and ingress-secret rotation invalidate the process-local browser session;
- `interaction_provider=lambda _interaction_id: None` is intentional: UI4 remains the first real selected-owner interaction proof.

Result: no material objection for repository scope.

### Iteration 4 — reversibility and minimization

Checks:

- install/start/status/restart/stop/uninstall are explicit and bounded;
- uninstall removes UI3 config, ingress secret and UI3 logs while leaving P7.04 credentials/grants untouched;
- rollback reconciliation removes UI3 when the resulting exact release predates UI3;
- raw P7.06 deployment outside the supported UI3 wrapper cannot make stale UI3 protected content valid: UI1/UI2 exact-release checks fail closed. The supported persistent path is the UI3 governed wrapper documented by the shell usage text;
- no remote transport client or wildcard/public listener is introduced.

Result: no material objection for repository scope.

### Iteration 5 — selected-Mac launchd readiness remediation

Selected-Mac Attempt 1 failed closed before service installation because no P7.04 human credential satisfied both exact local UI1/UI2 grants. A subsequent explicit owner-authorized P7.04 administrative step reused the existing owner-operated human principal and its single active credential, added/reused only `workspace.inspect / workspace:p7-06-ui1 / local` and `workspace.interact / workspace:p7-06-ui2 / local`, preserved deny-by-default/authority separation and left P7.03 governed/checkpoint state unchanged.

Selected-Mac Attempt 2 then reached UI3 launchd installation but failed with `UI3 launchd process has no private listener`. The operator report also established that the Python server could bind manually to `127.0.0.1:8766`; that observation does not by itself distinguish a startup-readiness race from occupation of the configured default port `8765`.

Material objection: `install_service()` waited only until launchd exposed a live PID and immediately entered strict `status_service()` listener verification. UI3 startup performs exact-release, P7.04 and UI1/UI2 checks before the server binds, so a healthy process could be observed before its private listener became ready. The lifecycle also lacked an explicit pre-start configured-port collision check, making an occupied port surface only as a generic post-start listener failure.

Revision:

- add bounded `wait_listener_ready` readiness polling for up to 20 seconds, requiring simultaneously a live exact launchd PID, listener ownership by that PID, exact `127.0.0.1:<port>` exposure and exclusive ownership of the configured port;
- use the same listener-readiness gate after install, restart and ingress-secret rotation rather than treating PID existence as readiness;
- after unloading any prior UI3 job, fail explicitly before launchd start if the configured private port is already occupied;
- retain the strict independent `status_service()` verification, exact-release plist pinning, private-material/log minimization and loopback/PID ownership checks unchanged.

Result: repository-side objection resolved. UI3 remains open because the selected Mac must activate the merged remediation through governed P7.06 update and rerun the full operational proof.

## Remaining closure gate

Repository implementation/review does **not** close UI3. Before roadmap status may become `Complete / PASS` and before UI4 becomes current, the selected owner Mac must prove the declared operational behavior against an exact merged release, including at minimum:

1. explicit existing P7.04 least-privilege admission for the selected human operator;
2. install and exact release/PID/listener status;
3. owner-local unlock without public ingress or secret leakage;
4. restart with prior browser-session invalidation and state integrity;
5. reversible uninstall/reinstall;
6. governed update/rollback reconciliation, including the pre-UI3 rollback case where applicable;
7. final read-after-write/runtime verification with no claim of real UI4 interaction evidence.

The P7.04 admission in item 1 is now satisfied on the selected Mac according to the bounded operator report, but items 2–7 require rerun against the merged launchd-readiness remediation. Until that proof exists, `P7.06-UI3` remains the current canonical action.
