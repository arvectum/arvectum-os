# P7.06-UI3 — Canonical governed controller review

Status: `Complete / PASS for repository remediation; selected-Mac execution pending`  
Task classification: `platform`  
Authority checked: Constitution `1.2.0` Ratified; RFC-0001, RFC-0003, RFC-0005, RFC-0006 Accepted; ADR index contains no applicable Accepted ADR.

This is a bounded operational integration remediation discovered after the P7.06-UI3 functional review reached its maximum 7/7 iterations. It does not reopen that functional review, change UI3 authority/security semantics, close UI3, promote lifecycle/readiness, or change a Product Contract.

## 1. Trigger

After selected-Mac forensics classified the prior blocker as `UPDATE_COMMAND_FAILED` and PR #66 added bounded runtime-consistency recovery, read-after-write review of the merged UI3 lifecycle path found a separate deterministic integration defect.

`p7_06_ui3_macos_operator.sh` historically resolved `p7_06_macos_deploy.sh` from `$RUNTIME_ROOT/releases/<current>/source/reference/python`. Runtime releases are immutable `git archive` snapshots of `reference/python`; they are intentionally not Git checkouts. Canonical `p7_06_macos_deploy.sh`, however, derives `REPO_ROOT` from its own location and requires that location to be a clean `main` checkout of `arvectum/arvectum-os`, fetching and fast-forwarding `origin/main` before update.

Therefore a release-snapshot copy of the deploy adapter cannot satisfy its own canonical-checkout precondition. Replaying that path during UI3 governed update/rollback would create a deterministic false failure even after runtime consistency was recovered.

## 2. Remediation

`reference/python/p7_06_ui3_canonical_governed_controller.py` establishes an explicit two-plane boundary:

- **deployment control plane:** current canonical Git checkout of `arvectum/arvectum-os` on clean synchronized `main`;
- **private presentation plane:** UI3 service Python/module/config/plist pinned to the exact release represented by runtime `current`.

The canonical governed controller:

1. verifies a real Git checkout/worktree;
2. requires branch `main`, clean tree, exact allow-listed canonical origin, successful `origin/main` fetch and `HEAD == origin/main`;
3. runs the unchanged canonical `reference/python/p7_06_macos_deploy.sh` from that checkout;
4. passes the selected runtime root explicitly through `ARVECTUM_P7_02_ROOT`;
5. if UI3 is loaded, verifies and stops it before the P7.06 operation;
6. after update/rollback, reconciles only the UI3 presentation surface against the actual resulting `current` release;
7. when that release contains UI3, uses the current canonical hardened UI3 shell to install/status an exact-current service;
8. when the resulting release predates UI3, removes only the bounded UI3 private surface paths and requires the launchd target/private material to be absent;
9. if P7.06 fails, still reconciles the resulting exact-current UI3 state before returning failure;
10. never selects a runtime release itself and never replaces P7.06 deployment semantics.

The supported selected-Mac proof runner now requires `--repo-root`, verifies canonical checkout `HEAD/origin-main == exact active proof target`, routes all P7.06 deploy calls to the canonical checkout controller, and keeps ordinary UI3 lifecycle calls on the hardened exact-target controller. Its attestation adds:

- `canonical_checkout_deploy_controller_verified = true`;
- `release_snapshot_deploy_controller_invoked = false`;
- `canonical_checkout_head_sha`;
- the existing hardened-controller / no-historical-controller-replay facts.

## 3. Review/revise

### Iteration 1 — canonical checkout trust and portability

Concern: the new control boundary must not accept an arbitrary repository path or accidentally exclude a valid Git worktree.

Resolution:

- repository validity uses `git rev-parse --is-inside-work-tree`, not the physical presence of a `.git` directory;
- branch must be exactly `main`;
- working tree must be clean;
- origin must equal one of the exact canonical HTTPS/SSH forms for `arvectum/arvectum-os`;
- `origin/main` is fetched;
- local HEAD must equal fetched `origin/main`;
- before a proof starts, canonical HEAD must also equal the exact active proof target release.

Result: `PASS`.

### Iteration 2 — exact-release reconciliation and historical rollback

Concern: using current canonical controller code after rollback must not cause historical service code to be silently replaced with target-release service code, and pre-UI3 rollback must remain reversible.

Resolution:

- the controller shell is current/hardened, but its existing install/status logic derives service Python/module/plist from runtime `current`;
- the canonical governed controller checks whether the resulting exact release contains the UI3 module;
- UI3-capable historical releases are installed/status-checked with their own exact service module and venv;
- pre-UI3 releases receive bounded cleanup only for the known UI3 plist/config/secret/log paths after the UI3 launchd job is stopped;
- P7.04 paths are not part of cleanup;
- direct historical deploy calls in the core proof are also routed to the canonical checkout deploy adapter.

Result: `PASS`.

### Iteration 3 — Governed Execution / failure semantics

Concern: a new wrapper must not become a deployment bypass or hide failed P7.06 outcomes behind successful UI reconciliation.

Resolution:

- canonical `p7_06_macos_deploy.sh` remains the only mechanism that changes P7.06 runtime release state;
- the controller has no target-release argument;
- update target resolution remains the canonical deploy adapter's existing `origin/main` path;
- rollback remains the existing `rollback-last` transaction path;
- UI reconciliation happens after the deploy result and does not convert deploy failure to success;
- if deployment fails, the controller reconciles the exact resulting current UI3 state and then still returns failure;
- P7.03/P7.04 integrity, no authority/approval, no product/external effect and no UI4 interaction remain proven by the existing selected-Mac core proof.

Result: `PASS`.

No material repository-scope objection remains after iteration 3. Selected-Mac execution remains required evidence.
