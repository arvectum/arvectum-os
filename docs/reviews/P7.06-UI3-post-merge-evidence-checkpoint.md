## Repository remediation result

PR `#62 — P7.06-UI3 — Remediate launchd listener readiness` merged to canonical `main` at `0d4d67fd0c1b7c4049cd96ebc4546983859f1563`.

The merged remediation:

- waits for a live exact launchd PID **and** its exact private listener readiness instead of treating PID existence as readiness;
- requires the listener to be owned by that PID and exposed only on `127.0.0.1:<configured-port>`;
- rejects any second listener/process sharing the configured port;
- fails explicitly before launchd start when the configured private port is already occupied;
- applies the readiness gate after install, restart and ingress-secret rotation;
- hardens multi-row `lsof` validation so an invalid later row cannot be overwritten by an `awk END` success exit;
- retains exact-release plist pinning, owner-only private material/logs, secret-log minimization and existing P7.04 authority separation.

## Controlled rerun sequencing

The selected Mac is currently reported on pre-remediation release `6d4d07aead603841ecce3c469dd46f5e0d58ccd5`. The UI3 proof runner exercises rollback to the source release of the most recent successful P7.06 update. Running the proof immediately after only one update from `6d4d07...` to the remediation merge would therefore roll back to the known pre-remediation UI3 lifecycle and could reproduce the already identified launchd race during rollback reconciliation.

The bounded closure rerun must therefore establish a remediated rollback source first:

1. governed P7.06 update `6d4d07... -> 0d4d67fd0c1b7c4049cd96ebc4546983859f1563`;
2. verify runtime/observer and P7.04 access on exact `0d4d67...`;
3. governed P7.06 update `0d4d67... -> <this checkpoint's merged canonical main SHA>`;
4. run `p7_06_ui3_selected_mac_proof.py` only from the exact final active release.

That arrangement makes the proof's rollback source and target both contain the remediated UI3 lifecycle while preserving real governed update/rollback semantics. It does not rewrite or bypass historical release behavior.
