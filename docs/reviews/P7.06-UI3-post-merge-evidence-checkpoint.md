## Rerun sequencing correction

The original version of this checkpoint proposed two governed updates so the proof would roll back to a remediated source release. Subsequent mandatory lookup of canonical `p7_06_macos_deploy.sh` showed that this is not a valid P7.06 operation: `assert_canonical_checkout()` fetches `origin/main`, fast-forwards local `main` to it and requires local `main == origin/main`. The governed update path therefore does not target an arbitrary historical SHA.

The underlying concern was valid: a direct update from selected-Mac release `6d4d07...` followed by proof rollback reaches that pre-remediation UI3-bearing source. The iteration-7 correction solves the problem at the UI3 presentation reconciliation layer instead of attempting to manipulate canonical deploy targeting.

The corrected bounded behavior is:

1. perform one ordinary governed P7.06 update from the selected Mac's current release to the then-current canonical `origin/main`;
2. run the exact target release's UI3 selected-Mac proof;
3. when proof rollback returns to historical `6d4d07...`, the **invoking hardened target controller** reconciles the private presentation process while pinning its Python/module/plist to the actual historical current release;
4. the historical lifecycle shell is not replayed merely to install the historical service, so its known startup-readiness race cannot be reintroduced by migration orchestration;
5. once the historical exact-release service is already listener-ready, the proof can safely verify historical `status` and use its governed forward update path; forward reconciliation reaches the new hardened current shell;
6. canonical P7.06 update/rollback semantics, current-release identity, P7.03/P7.04 state and service exact-release verification remain unchanged.

This correction is implemented and reviewed as functional cross-review iteration 7 of maximum 7. The previous two-step SHA-staging instruction is withdrawn and must not be used.
