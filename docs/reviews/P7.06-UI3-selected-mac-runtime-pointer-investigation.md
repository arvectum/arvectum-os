## Canonical P7.06 finding

Canonical `reference/python/p7_06_macos_deploy.sh` does not define a background rollback watcher. A source release is restored only through bounded deployment/recovery paths:

1. synchronous failed-update rollback via `rollback_and_record_failure()`;
2. explicit `rollback-last`;
3. explicit interrupted-work recovery.

A successful `update` records a `PASS` transaction, writes `run/p7-06-last-success.json`, prints `update PASS`, releases the deployment lock and returns. Explicit rollback/recovery paths create corresponding owner-local P7.06 evidence. Therefore a `current` mutation observed **after a completed `update PASS`** can be classified from P7.06 evidence rather than inferred from timing alone.

RFC-0006 requires meaningful operational behavior and incomplete/uncertain evidence paths to remain observable rather than silently represented as successful. The diagnostic below is therefore non-canonical operational telemetry/evidence and does not become organizational authority.

## Diagnostic runner

`reference/python/p7_06_current_pointer_forensics.py` performs one ordinary canonical P7.06 update from the canonical repository checkout and then watches `current` for a bounded window.

It records only minimized facts:

- source release and canonical `origin/main`;
- update exit code and redacted bounded stdout/stderr tails;
- `current` immediately after the **completed** update command and every subsequent observed transition;
- whether the P7.06 deployment lock exists at a transition;
- minimized relevant process facts at transitions;
- selected launchd loaded/PID/program-basename facts for runtime, observer and UI3;
- P7.06 last-success pointer fields excluding backup paths;
- new P7.06 evidence file basenames/digests and bounded rollback/recovery facts;
- before/after P7.03 governed/checkpoint and P7.04 access-store/secret digests.

The runner never invokes rollback, recovery or UI3 lifecycle operations. It does not create/change P7.04 access and does not mutate P7.03 governed/checkpoint state.

Possible classifications:

- `STABLE_AFTER_UPDATE` — completed update remains on canonical target for the watch window;
- `UPDATE_COMMAND_FAILED` — P7.06 update itself did not complete successfully;
- `EXPLICIT_P7_06_ROLLBACK_EVIDENCE` — post-update mutation is accompanied by new canonical P7.06 rollback evidence;
- `EXPLICIT_P7_06_RECOVERY_EVIDENCE` — mutation is accompanied by interrupted-recovery evidence;
- `UNATTRIBUTED_CURRENT_MUTATION` — `current` changes after a successful update without new P7.06 rollback/recovery evidence.

The last classification is deliberately diagnostic, not an accusation about a specific process. It means only that the observed pointer mutation is not attributable to the canonical P7.06 evidence path captured in the watch window.
