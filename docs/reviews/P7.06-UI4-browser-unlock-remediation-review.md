## 2. Root cause

UI3 unlock reuses `p7_06_ui2_governed_interaction._security_headers()` and
`_require_same_origin()`.

Before remediation the response combined:

- `Referrer-Policy: no-referrer`; and
- a strict POST requirement that `Origin` equal the exact loopback origin.

For ordinary non-CORS browser form navigation, `no-referrer` may cause a user agent to serialize the request Origin as `null`. The result is a self-conflicting browser contract: the response policy can suppress the exact request metadata that the following POST requires.

The observed absence of `Access denied.` is consistent with the pre-secret `same-origin/form` failure branch, while the direct diagnostic with the exact Origin proves the retained secret, server-side CSRF continuity, session creation and authenticated workspace/UI4 routes are otherwise operational.

## 3. Bounded remediation

The remediation changes only the shared private UI response policy:

```text
Referrer-Policy: no-referrer
        ↓
Referrer-Policy: same-origin
```

`same-origin` preserves referrer information only within the same origin and suppresses it to other origins. This allows an ordinary same-origin loopback form navigation to preserve the browser origin context needed by the existing strict POST check without disclosing the referrer cross-origin.

The following security boundaries are unchanged:

- exact IPv4 loopback listener and Host boundary;
- exact `Origin == http://127.0.0.1:<configured-port>` requirement;
- missing Origin remains denied;
- `Origin: null` remains denied;
- cross-origin and wrong-port Origin remain denied;
- CSRF continuity remains required;
- owner-local ingress secret remains required;
- process-local HttpOnly / SameSite=Strict session remains unchanged;
- P7.04 exact human local grants remain prerequisites;
- technical access still creates no Organizational Authority or consequential approval;
- UI4 remains preflight-only and creates no canonical mutation or product/external effect.
